VDS Planner: operator guide

This guide tells the operator how to make the VDS plan of one vCenter with the VDS Planner, and how to apply the plan with PowerShell. All values in this guide are examples.

Summary
  • The planner is one HTML file. Open it in Microsoft Edge. It needs no install and no server. It cannot connect to a network.
  • The input is the inventory workbook (.xlsx) of the vCenter, full or only its network sheets, CSV exports of those sheets, or the export of Export-VssLayout.ps1 (T-01). The planner reads the workbook on this computer and makes the project file (JSON). It does not change the inventory.
  • A project holds one vCenter. Each draft tab is one plan. A draft can have many VDS. A VDS can be for one cluster (the standard) or for more clusters (V-08 only).
  • A commit makes a package of four files. Invoke-VdsPlan.ps1 applies the package. It stops if the plan file changed after the commit.

2. Start from an inventory workbook

If an inventory workbook (.xlsx) of each vCenter is available, the planner needs no connection to vCenter to start. There are two methods. Both give the same inventory.

Method A: in the planner

  1. Open planner\vds-planner.html in Edge. Select Import inventory.
  2. Select the workbook of one vCenter. You can select the full workbook, a workbook with only the network sheets, or CSV exports of the sheets (one file for each sheet, with a comma, semicolon or tab between the values). The planner finds each sheet by its name, by the file name or by its columns. It ignores the other sheets.
  3. The Inventory workbook window shows the sheets that it found, the number of clusters, hosts, switches to convert and port groups, and notes about missing sheets:
    SheetThe planner uses it forIf the sheet is missing
    vPortPort groups, VLANs, security and teamingNecessary. The planner cannot make the project.
    vNICUplinks and NIC speedsEach VDS has no uplink. Rule V-02 blocks the commit.
    vSwitchStandard switches and their MTUThe switches come from the port groups. The MTU is not known.
    vHostClusters, datacenters, ESXi versions, vCenter nameClusters and datacenters come from the network sheets. The ESXi version check is not possible.
    vSC_VMKVMkernel port groupsThe VMkernel port groups are not marked.
    dvSwitch, dvPortPort group names that existing VDS useThe planner cannot find names already in use. Invoke-VdsPlan.ps1 still checks them before a change.
  4. Enter the site name and select Make the project (or New project from the workbook). The project gets the same two drafts as method B. If a project is open, Refresh the inventory of this project shows the differences first and keeps the drafts and the zones.
  5. Select Save the project file. The project file (<site>.vdsplan.json) holds the inventory and the drafts. Keep it in your environment.

The input of one project must be from one vCenter. The planner blocks input from more than one vCenter. Hosts with no cluster are not in the plan.

Method B: the preload script, with the simulation

  1. Run the preload for all vCenters: 
    .\scripts\inventory\Export-PlannerPreload.ps1 -Workbook .\inv\prd.xlsx, .\inv\dr.xlsx -Site PRD, DR -OutputFolder 'D:\VDS Planner'
  2. Open index.html in the output folder. It shows each site, the number of switches to convert and the result of the simulation.
  3. Read the readiness report of the site. It shows the VDS that are ready, the blocking items by rule, the duplicate names, the name clashes and the hosts that miss port groups.
  4. In the planner, select Open project and select <site>\inventory\<site>.vdsplan.json. The project has two drafts:
    • Standard layout (V-01): one VDS for each standard switch, with the port group names of the standard switches.
    • Standard layout (V-01), names fixed: the same, with names that vCenter accepts. A name that is on one VDS with different VLANs gets the VLAN at the end. A name that is on more than one VDS of a datacenter gets the cluster name in front.
  5. Continue with section 4. The inventory of the workbook has the same columns as the export of Export-VssLayout.ps1.
Port group names in one datacenter. vCenter needs a unique distributed port group name in a datacenter. When many clusters of one datacenter have the same port group names, one VDS for each cluster (V-01) is possible only with new names. The draft names fixed gives these names. The VM moves use the new names, and the VMs show them. A shared VDS for clusters with the same switches (V-08) keeps the names. This is a design decision.

3. Before you start (live export)

  1. Install PowerCLI 13 or later on the jump host. Copy the toolkit to a folder, for example C:\Tools\vds-toolkit.
  2. Connect to the vCenter. Run Export-VssLayout.ps1 for each cluster: 
    Connect-VIServer -Server vc01.example.local -Credential (Get-Credential)
.\scripts\inventory\Export-VssLayout.ps1 -Cluster Cluster01
    The script writes Cluster01_hosts.csv, Cluster01_portgroups.csv and Cluster01_vdsplan.csv to .\output\. The files include the datacenter of the cluster and the ESXi version of each host. The planner uses them for the port group name check and the version check.
  3. Open planner\vds-planner.html in Edge. Enter the vCenter name and the site.
  4. Select Import inventory. Select the _vdsplan.csv and _hosts.csv files of all clusters. The planner does not need _portgroups.csv. An inventory workbook is also possible (section 2).
  5. In the inventory column, set the security zone of each cluster (Internal, DMZ and more). The shared VDS check (V-08) uses the zone.
  6. Select Settings. Enter the toolkit folder on the jump host and the vCenter user. The default user is administrator@vsphere.local.
  7. Select Save project. Save the project file in your environment.

4. Make the plan

Help on the page. The guide bar at the top of the planner stays in view. It shows eight steps: Inventory, vCenter, Draft, Add VDS, Checks, Commit, Save and Run. A green step is done. The blue step is the next action. The line Next: tells you what to do, and its button does it or shows you where it is. The Commit button is always at the right of the guide bar. Put the mouse pointer on a button or a field: a help bubble tells you what it does. The bubble goes away when the pointer moves. ? Help starts the guided tour again and turns the help bubbles on or off. The planner shows the tour offer when you open it for the first time.

Menus and files. The menu bar works like a desktop application. File: New project (Ctrl+Alt+N), Open project (Ctrl+O), Open the demo project, Save (Ctrl+S), Save as (Ctrl+Shift+S), Close project, Import inventory (Ctrl+I), Project settings and the recent projects. Edit: Undo (Ctrl+Z), Redo (Ctrl+Y), Find port groups (Ctrl+F), Preferences. Draft: new, duplicate, rename (F2), delete, Add all switches, Fix names, Commit (Ctrl+Enter). View: Environment and drafts, expand and collapse, theme (system, light, dark), help bubbles. Tools: self-test. Help: how to use, tour, keyboard shortcuts, the operator guide and About. When no project is open, the start screen shows the first steps and the recent projects. The status bar at the bottom shows the file, unsaved changes, the vCenter, the open draft and its blocking checks. Undo never removes the record of a committed version. If the browser closes with changes that are not saved, the planner offers a recovery copy at the next start. The recent list, the preferences and the recovery copy are in the browser storage of this computer only. A release with a brand shows a logo and a light watermark. Edit, Preferences, Branding turns them off. The generated report then has no logo. Recent projects and Save to the same file need Microsoft Edge or Google Chrome. Other browsers download the file.

The draft view. Each VDS shows as a diagram, like the switch view of a host in the vSphere Client. The port groups are on the left, with the VLAN, the port binding and the VMkernel ports. Each port group has a line to the bus. The Uplinks box is on the right, with dvUplink1, dvUplink2 and more. It shows the physical adapters (for example vmnic1 (6)) that each uplink gets on the hosts. Physical adapters of n hosts opens a table for each host. The map is the result of Move-HostToVds.ps1: stage 1 moves vmnic1 to dvUplink1, and stage 2 moves the other adapters. When you select a port group, its line and its box are orange, and the Uplinks box shows each uplink as Active, Standby or Unused for that port group. The Uplinks box and the VDS name stay in view when you scroll a long list. The arrow next to the VDS name folds the VDS. Expand all and Collapse all do this for all VDS. The filter shows only the port groups with a name or a VLAN ID that contains the text.

The Environment tab shows each standard switch of each cluster and its status: not planned, in draft or committed. Use it to make sure that the full environment has a plan.

  1. Select a draft tab, or + New draft. Double-click a tab to rename it. Duplicate draft makes a copy to try a different plan.
  2. In the inventory column, select Add all switches, or select Add next to one switch. The planner makes the VDS with the name of rule V-01 (<cluster>-vds01 for vSwitch0). It adds all port groups of that switch.
  3. Select a port group to set it. The settings are in the right column:
    SettingValuesDefault
    Create this port groupOn or offOn
    Name on the VDSText, 80 characters or lessName of the standard port group
    VLAN typeNone, VLAN, VLAN trunkingFrom inventory. VLAN 4095 becomes trunk 0-4094.
    Port bindingStatic, EphemeralStatic
    Number of ports1 to 8192 (static only)8
    Port allocationElastic, Fixed (static only)Elastic
    Load balancingOriginating virtual port, source MAC hash, IP hash, physical NIC load, explicit failover orderOriginating virtual port (V-09)
    Failover orderActive, Standby or Unused for each uplinkAll uplinks active
    SecurityPromiscuous mode, MAC address changes, forged transmits: Reject or AcceptReject
  4. Copy these settings to all port groups copies the binding, ports, allocation, teaming and security to the other port groups of the VDS. It does not copy the name or the VLAN.
  5. A large VDS can have hundreds of port groups that are not on all hosts (V-05). When the network team confirms the VLAN trunk for a VDS, select the VDS header and set the trunk check for all of them at one time.
  6. Fix names on the draft renames the duplicate names and the names that clash in a datacenter, with the same rules as the draft names fixed.
  7. + Port group adds a port group that is not in the inventory, for example the ephemeral port group for the vCenter VM (V-09).
  8. Select the VDS header to set the VDS name, the version (8.0.3 is the design value) and the MTU (1500 is the design value). A new vMotion or Provisioning adapter sets the VDS MTU to 9000.
  9. The VDS version must not be later than the ESXi version of all hosts. A host with ESXi 8.0.2 cannot join a VDS 8.0.3. The planner blocks this. Upgrade the host or select VDS 8.0.0.
  10. A distributed port group name must be unique in its datacenter. One VDS for each cluster often gives the same names (for example Management Network) on two VDS in one datacenter. The planner shows this. Select the VDS header, then Add a name prefix, for example Cluster01-. Invoke-VdsPlan.ps1 also stops before any change if a name is on another VDS in the datacenter.

5. Shared VDS for more than one cluster (V-08)

The standard is one VDS for each standard switch of each cluster (V-01). One VDS can also serve more than one cluster. The planner checks two kinds of conditions:

ConditionKindResult
The clusters are in the same datacenter (a VDS is in one datacenter only)NecessaryBlock
The clusters have a security zone, and it is the same zone. DMZ and internal clusters never share a VDS.NecessaryBlock
Each cluster has two uplinks or more on the switch (V-02)NecessaryBlock
The uplink names are the sameDesign decisionYou accept the difference
The NIC speed is the sameDesign decisionYou accept the difference
The port group names and VLANs are the sameDesign decisionYou accept the difference

There are three methods to put a cluster on a VDS, or to move it from one VDS to another:

  1. Drag the switch of the cluster from the inventory column onto the VDS. Drop it next to the VDS boxes to give the cluster a VDS of its own.
  2. Select + Cluster on the VDS. The planner shows the switch of each other cluster, where it is now, and the result of the check. Select Add, or Move here for a cluster that is in another VDS.
  3. Select the VDS name. In the settings panel, each cluster has a Move ... to list: another VDS of the draft, or A VDS of its own. Remove takes the cluster out of the VDS. Its switch is then free in the inventory.

If the clusters are not the same, the planner shows the differences. Select Accept and add (or Accept and move) to continue. Then:

  • The VDS gets the port groups of all its clusters. A port group that is on all clusters is one port group. A port group that is not on all clusters gets the flag Not on <cluster> and needs the VLAN trunk check (V-05).
  • A port group name with a different VLAN on two clusters is on the VDS two times. The name check blocks this. Select Fix names to add the VLAN to the names.
  • The VDS gets the largest number of uplinks of its clusters. On hosts with fewer adapters, the last uplinks stay empty. The planner warns.
  • When a cluster leaves a VDS, the port groups that only that cluster had leave the VDS too. A VDS with no cluster leaves the draft.
  • The plan file records v08Check: accepted and the accepted differences (v08Accepted). The report shows them. Test-VdsPlan refuses a VDS for more than one cluster that has neither pass nor accepted with a list.

If the inventory changes later and new differences show, the commit is blocked until you select Accept the differences on the VDS again, or move the cluster. Change the VDS name if necessary, for example to a name for all its clusters.

6. New VMkernel adapters

The VMkernel adapters of the inventory are fixed. The planner can add new adapters, for example a dedicated vMotion adapter (RW-07).

  1. Select + VMkernel on the VDS. The planner adds a vMotion adapter and a dedicated port group with explicit failover order.
  2. Set the service (vMotion, Provisioning, Management, vSAN, FaultTolerance, Replication, NfcReplication) and the TCP/IP stack. The vMotion stack is for vMotion only. The Provisioning stack is for Provisioning only. The stack cannot change after ESXi creates the adapter.
  3. Select the port group, or + New dedicated port group. Set the VLAN and the failover order on that port group.
  4. Set the MTU. The default MTU is 9000 for vMotion and Provisioning, and 1500 for the other services. Change it if necessary. If the adapter MTU is larger than the VDS MTU, the planner sets the VDS MTU to the same value. The physical switches must then support that MTU on all uplinks of all hosts.
  5. For vMotion: select Turn off vMotion on vmk0 to stop vMotion on the management adapter after the new adapter is up.
  6. Enter a static IP address and a subnet mask for each host. Fill from a first IP gives the next addresses to the next hosts. Import IP plan CSV reads a CSV with the columns Host, IP, SubnetMask. DHCP is not permitted (RW-09).

7. Commit and generate the package

  1. Correct all block items in the checks panel. While a block item exists, the Commit button shows the number of blocking items and takes you to the checks. Read the warn and info items.
  2. Select Commit at the right of the guide bar (or Commit and generate package at the bottom of the page). The commit window shows the vCenter, the vCenter user, the toolkit folder, the checks and the 4 files that the planner writes. Enter your name. Select Commit and select a folder.
  3. Select an empty folder for the package. A browser with no folder picker puts the files in the Downloads folder.
  4. The Package window opens. It shows the folder, the 4 files (select View to read a file, or Open for the report) and the PowerShell commands to run on the jump host, each with a Copy button. For security the browser gives the planner only the folder name, not the full path.
  5. Select Save project. The committed version is in the project file only after you save it.
  6. A committed version does not change. To change the plan, edit the draft and commit again. This makes version n+1.
  7. How to run next to a version opens the Package window again. Generate again writes the files of a committed version again. The plan file and its hash are the same as at the commit.

8. Run the package

  1. Put the four package files in one folder on the jump host.
  2. Before the change window, run the preflight. It is read-only. It shows READY or a list of blocking items. 
    .\Invoke-shared-db-vds-v1.ps1 -Part Check
  3. Run the launcher with -WhatIf. It asks for the credential, connects and shows each step. It does not change anything. 
    .\Invoke-shared-db-vds-v1.ps1 -WhatIf
  4. Examine the output. A warning for a host with a different uplink layout (V-06) means that you must correct that host first.
  5. Under the change control of your organization, run the launcher with no -WhatIf. Answer each confirmation prompt. The script creates the VDS and the port groups and adds the hosts with no uplink. A VDS or a port group that exists is not changed.
  6. Move each host and the VM networks with Move-HostToVds.ps1 and Move-VmNetworkToVds.ps1.
  7. If the plan has new VMkernel adapters: for each host, after stage 2, run: 
    .\Invoke-shared-db-vds-v1.ps1 -Part VMkernel -VMHost esx11.example.local -WhatIf
.\Invoke-shared-db-vds-v1.ps1 -Part VMkernel -VMHost esx11.example.local
  8. Keep the transcripts and the CSV logs of .\output\, and the report of the package, with the change record.
Stop conditions. Invoke-VdsPlan.ps1 does all read-only checks before it changes anything. It stops when the hash of the plan file is not correct, when the plan has errors, when the session is connected to a different vCenter, when a cluster is missing, when the clusters of a VDS are in more than one datacenter, when a host is not connected, when a host runs an earlier ESXi version than the VDS, when a VDS exists with different uplinks, when a port group name is on another VDS in the datacenter, or when a planned IP address is in use on another host.

9. Inventory refresh

  1. Run Export-VssLayout.ps1 again for the clusters that changed.
  2. Select Import inventory and select the new files. The planner shows the changes: port groups and hosts that are added, removed or changed.
  3. Select Apply. The checks of each draft show the VDS that need an update.
  4. Select the VDS header, then Sync from inventory. The planner adds the new port groups, stops the port groups that are not in the inventory now, and updates the uplinks. A VLAN that you changed stays as you set it.
  5. For a VMkernel adapter, select Update host list.

10. Rollback in the pilot

  1. Move the VM adapters back: Move-VmNetworkToVds.ps1 -RollbackCsv <file>.
  2. Move the VMkernel adapters and the uplinks of each host back to the standard switch (vSphere Client, one host at a time).
  3. Remove the VDS. The script removes it only when no host has an uplink or a VMkernel adapter on it, and no VM uses its port groups: 
    .\scripts\network\Remove-VdsPlanSwitch.ps1 -PlanFile .\plan-shared-db-vds-v1.json -VdsName DB-shared-vds01 -WhatIf
.\scripts\network\Remove-VdsPlanSwitch.ps1 -PlanFile .\plan-shared-db-vds-v1.json -VdsName DB-shared-vds01

13. Security

  • The planner page has a content security policy that blocks all network connections. It loads no external file.
  • No file holds a credential. The launcher asks with Get-Credential at run time.
  • The project file and the package hold environment data. Keep them in your environment. Do not put them in the toolkit repository.
  • The SHA-256 hash file protects the plan file. If somebody edits the plan file, Invoke-VdsPlan.ps1 stops.

14. Limits of this version

  • The scripts have not run against a vCenter. Run the live test checklist on a lab vCenter before the pilot.
  • The planner does not set a gateway for the vMotion or Provisioning TCP/IP stack. Use one layer 2 network for these adapters, or set the gateway on the host.
  • Private VLANs, traffic shaping and NetFlow are not in the planner.
  • The planner does not remove a VDS or a port group. To roll back, use the rollback CSV of Move-VmNetworkToVds.ps1 and remove the VDS in vCenter.
